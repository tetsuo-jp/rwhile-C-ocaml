# 夜間の資源移設と初回運転の準備（2026-08-09 深夜）

朝いちばんに読む 1 ファイル。**結論から**:

- **夜間ランナーは owari から s3 へ移した。** 理由は今夜の混雑ではなく**構造的なメモリ不足**
- **owari の 03:30 タイマーは止めてある**（`systemctl --user disable --now autoresearch-rwhile.timer`）
- **s3 のタイマーを 03:30 で有効化した**（`Linger=yes` なのでログアウト中も走る）
- この機械（mikawa）のタイマーは**止めたまま**。二重実行を避けるため

## 1. なぜ owari を諦めたか（測定）

**Agda の「冷たい」検査は、単一モジュールで 6.3〜9.8GB 要る。**

| 機械 | 総メモリ | 結果 |
|---|---:|---|
| owari | 7.6GB | **完走できず**。RSS 6.99GB まで伸び、available が 51MB・swap 4094/4095 まで枯渇 |
| s3 | 16.0GB | **完走**（`PASS=125 FAIL=0`）。ピーク RSS **9.8GB** |
| mikawa | 61GB | 507MB に見えていた——**`_build` キャッシュが効いていたから**。冷たい状態の値ではない |

読み替えるべき点が 2 つ:

- **手元の実測を遠隔機に当てはめると外す。** 「Agda 検査は 500MB」は暖かい機械の数字だった
- **分割はもう効かない。** この形式化は既に 125 モジュールに分かれている（最大 48KB）。
  それでも単一モジュールが 9.8GB を要求する。**要るのは 10GB 以上の機械**

したがって owari は、明日メモリが戻っても Agda のゲートを持つこのジョブには**戻さない方がよい**。
夜間ループはモジュールを書き換えるのが仕事なので、暖かいキャッシュを毎晩壊しにいく。

### 今夜の事故（自己申告）

owari の available を 51MB まで落としたのは**私が 22:11 に始めたキャッシュ温め**（`./check.sh`）である。
s3 に同じものを立てた時点で重複していた。指揮者セッションから指摘を受けて停止した。

- `pkill -f "check.sh"` は**効かなかった**。ssh のコマンド行自体が文字列に一致し、自分を殺していた
- `P=$(pgrep -f "chec[k].sh")` のように**自分に一致しない書き方**にして PID 直指定で解決
- 停止後: available 51MB → **6936MB**、agda・check.sh とも 0 件

## 3. 移設で見つかった harness の欠陥（3 件、すべて修正済み）

| # | 欠陥 | なぜ危ないか | 修正 |
|---|---|---|---|
| 1 | パスに `/home/a` を焼き込んでいた | s3 のホームは `/home/tetsuo`。**黙って壊れる** | スクリプトの位置から導出（`84be8d3` 前） |
| 2 | `systemd --user` は brew / opam / `~/.local/bin` の PATH を失う | `ocamlfind` も `claude` も見つからず **rc=127 で静かに死ぬ** | `opam env` を取り込み PATH を自力補完。**必須コマンドが無ければ即エラーで落とす**（`84be8d3`） |
| 3 | unit にメモリ上限が無かった | 10GB 級の Agda が kernel OOM を引く。**OOM kill は検査器の沈黙と区別がつかない** | `MemoryMax=10G`（systemd が殺せば理由がログに残る）+ `Nice=19` |

3 番は今日の教訓（`~/.claude/rules/shell.md`「検査器・ビルドの沈黙は成功ではない」）そのものの型である。

## 5. 今日この harness が捕まえた不正（朝の判断材料）

**受入コマンドの人間チェックが、実運用の初回で 1 件捕まえた。** モデルが書いたのは

```
cd src && make run-tests 2>&1 | grep -c 'test_fp1_dyncond_known_bug' \
  && ! ./test-suite test dyn-cond 2>&1 | grep -q 'error in update'
```

- 群名 `dyn-cond` は**存在しない**（正しくは `dyn-control`）
- `test_fp1_dyncond_known_bug` は OCaml の関数名で、Alcotest の出力には**決して現れない**

つまり**課題を完全に解いても永久に通らない**。事前 FAIL 検査は「いま落ちる」しか見ないので、
**壊れたコマンドも「解くべき課題」として通してしまう**。`validate_accept.py` を入れて塞いだ
（存在しない群・出力に現れない識別子の grep・危険な操作・既存ゲート未使用の 4 点）。

**朝に見るべきはここ。** 静的検査は同型のものを弾くが、「緩い judge」は依然として人間の目でしか
判定できない。4 条件が緑でも、判定が緩ければ意味がない。
