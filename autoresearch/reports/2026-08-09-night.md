## 1. なぜ owari を諦めたか（測定）

**Agda の「冷たい」検査は、単一モジュールで 6.3〜9.8GB 要る。**

| 機械 | 総メモリ | 結果 |
|---|---:|---|

読み替えるべき点が 2 つ:

- **手元の実測を遠隔機に当てはめると外す。** 「Agda 検査は 500MB」は暖かい機械の数字だった
- **分割はもう効かない。** この形式化は既に 125 モジュールに分かれている（最大 48KB）。
  それでも単一モジュールが 9.8GB を要求する。**要るのは 10GB 以上の機械**

したがって owari は、明日メモリが戻っても Agda のゲートを持つこのジョブには**戻さない方がよい**。
夜間ループはモジュールを書き換えるのが仕事なので、暖かいキャッシュを毎晩壊しにいく。

### 2 本目で露呈した設計の矛盾（私の落ち度）

Opus は指示どおり「これから作る群」を指したのに、静的検査が「存在しない群」として弾いた。

- プロンプト側:「pin を閉じる課題は**これから作る新しい群**を指せ」（緑の群を指す袋小路を避けるため）
- 静的検査側:「**存在しない群**を指すな」（`dyn-cond` の綴り間違いを弾くため）

課題 JSON に **`creates`**（これから作る群）を宣言させ、宣言があれば許す形にした。
宣言が無ければ従来どおり弾き、**近い既存群を提示**する。

### さらに `creates` は検算しないと逃げ道になる

綴り間違いを `creates` に書けば静的検査を素通りできる。そこで**事後検証に 2 項目**足した:

1. **`creates` に挙げた群が run 終了時点で実際に存在するか**。無ければ
   `accept_cmd` の exit code に関わらず**受入は不成立**
2. **差分ゼロの検出**。`REV_BEFORE = REV_AFTER` なら
   「**run は完了したが本題は 1 行も進んでいない**」を出し、合格条件から外す

> ⚠ **この 2 項目は明日の run から効きます。** 今夜 06:35 に出るレポートの判定行には
> `creates=` と `差分=` が出ません（走行中の run は配備前のチェックアウトを使っているため）。
> **今夜は従来どおり `accept` / `tests` / `fp2` / `probe` の 4 つで読んでください。**
> 判定行にこの 2 つが無いことは、壊れている印ではありません。

### 塞ぐためのコード自体にも同じ型のバグが出た

`note "- ✗ **\`creates\` に挙げた群…"` と Markdown のつもりで書いたバッククォートを、
**シェルが `creates` というコマンドとして実行しようとしていた**。保存フックの shellcheck が
SC2006 で捕まえた。**「もっともらしく見えるものを検算せずに通す」型が、それを塞ぐコードに出た**。

## 5. 今日この harness が捕まえた不正（朝の判断材料）

**受入コマンドの人間チェックが、実運用の初回で 1 件捕まえた。** モデルが書いたのは

```
cd src && make run-tests 2>&1 | grep -c 'test_fp1_dyncond_known_bug' \
  && ! ./test-suite test dyn-cond 2>&1 | grep -q 'error in update'
```

- 群名 `dyn-cond` は**存在しない**（正しくは `dyn-control`）
- `test_fp1_dyncond_known_bug` は OCaml の関数名で、Alcotest の出力には**決して現れない**

つまり**課題を完全に解いても永久に通らない**。事前 FAIL 検査は「いま落ちる」しか見ないので、
**壊れたコマンドも「解くべき課題」として通してしまう**。`validate_accept.py` を入れて塞いだ
（存在しない群・出力に現れない識別子の grep・危険な操作・既存ゲート未使用の 4 点）。

**朝に見るべきはここ。** 静的検査は同型のものを弾くが、「緩い judge」は依然として人間の目でしか
判定できない。4 条件が緑でも、判定が緩ければ意味がない。
